# 0.2.166 · 빌드 193

화면의 정확한 동일성 비교에서 Swift가 연속 UTF-8 버퍼를 제공하면 길이와 공유 저장소를 먼저 확인하고, 끝 128바이트와 나머지 본문을 memcmp로 비교합니다. Cocoa 문자열끼리는 같은 불변 NSString 객체를 공유하면 중복 읽기를 생략합니다. 객체가 다르면 129-unit 임시 버퍼로 마지막 128개 repaired UTF-16 unit을 먼저 검사합니다. 선행 unit 하나로 surrogate 경계를 보존하며, 끝부분이 같아도 전체 동일성을 계속 확인합니다. 혼합 저장소와 표시용 정규화 비교는 유지합니다. 새 내용·객체 캐시나 폴링·상주 서비스를 만들지 않았습니다.

오류 분류기는 소문자화한 셀의 오류 접두사 또는 용량 부족 특례의 첫 유효 문자를 먼저 확인합니다. 일반 셀은 전체 문자별 공백 제거를 건너뜁니다. 공백 없는 용량 부족 문구·Unicode 선행 공백, 정확한 Codex/Claude 오류 접두사와 인증·설정 오류 우선순위는 유지합니다. 실행 스택에서 이 경로를 확인한 뒤 정식 분류기와 직접 비교했습니다. 단독 시제품의 일반 셀 분류 CPU는 약 65~75% 줄었지만, 그 수치를 아래 실제 Core나 앱 전체 개선율로 사용하지 않습니다.

비변경 화면 갱신의 CPU는 native **52.1~56.4%**, Cocoa **15.8~22.5%** 감소했습니다. 변경 화면의 결과도 아래에 함께 공개하며 모든 사전 기준을 통과했습니다.

실제 최적화 정식 0.2.165와 후보 Core를 새 프로세스 16개·8쌍으로 교대 실행하고 문자열 종류 순서를 회전했습니다. 합성 16세션을 종류별 변경/비변경 각각 256회 갱신한 CPU·wall 합계의 8회 중앙값입니다. 변경 시 모든 과거 본문이 바뀌고 4개 입력 대기의 tail은 그대로이며, 나머지 표시 variant도 고정 fixture를 따릅니다. 준비와 2.2초 정착은 CPU/wall 밖, RSS에는 포함됩니다. helper 선택 시간이나 이전 비교 표본은 재사용하지 않았습니다. 앱 전체·실제 휴대폰·네트워크/VPN의 종합 개선율은 아닙니다.

사전 기준은 Cocoa 비변경 CPU ≤0.85배, 나머지 CPU ≤1.05배, 모든 wall ≤1.10배, 최대 RSS ≤max(기존×1.10, 기존+1MiB)였습니다. 4종류·8작업량·모든 표본을 유지했고 상태·발행 수·실제 저장 형태도 일치했습니다.
