# Codex 계정 확인·변경과 세션 그룹 통합·분리 설계

날짜: 2026-11-04
상태: 독립 구현자 검토 반영 · 구현 전 설계 확인
목표 원문: “코덱스 로그인 확인과 로그인 계정 변경 각각 독립적인 세션의 통합과 분리를 개선하고 속도와 안정성을 향상시키자.”

## 사용자 요구와 현재 증거

- 사용자는 로그인 변경을 열린 세션에 반영하고, 특정 세션은 별도 계정으로 로그인할 수 있기를 요청했다. 창·탭·대화와 Goal을 보존하고 작업은 순차 중단한 뒤 실제 연결을 검증해야 한다.
- 다른 Apple Silicon Mac의 별도 진단 셸에서 CLI login status 0.17초, --version 0.08초, daemon version 0.25초, 새 zsh -lic 초기화 4.22초를 관찰했다. 현재 ChatGPT 로그인, daemon 0.166.0 running, daemon_auto_start=true, 원본 세션 3개 유지였다. 실제 다른 계정의 브라우저 인증은 아직 재현하지 않았다.
- 0.2.249는 서버 조회의 각 명령에 새 로그인 셸을 사용하고, 진단은 6초 제한이다. 네이티브 계정 UI의 loading은 서버 조회와 로그인 조작을 함께 막는다.
- 세션별 계정 화면은 공유 세션 수를 표시하지만 실제 분리/통합 동작은 없다. 현재 로그인 확인 버튼은 자동 전환과 묶여 있어 순수 조회로 볼 수 없다.
- 설치된 0.166.0의 생성 스키마에 accountSession/list와 accountSession/switch가 있다. thread/start/resume에는 명시적인 계정별 바인딩 필드가 확인되지 않았다. 이 버전의 실제 프로토콜로 검증하고 미래 버전을 추측하지 않는다.

## 접근 방식

1. **기존 관리형 서버 + 계정 그룹별 독립 CODEX_HOME (추천)**: 기존 순차 중단/연결 저널을 재사용한다. 같은 홈은 같은 계정을 공유하고, 독립 계정은 별도 홈/서버로 분리한다. 조회는 빠른 native CLI/공식 읽기 API로 분리한다. 지원되는 계정 전환 API는 실제 검증을 거쳐 사용한다.
2. **서버 하나에서 세션별 계정 덮어쓰기**: 현재 생성 스키마에서 세션별 인증 바인딩을 확인하지 못했다. 설정만으로 격리를 약속하면 다른 세션까지 계정이 바뀔 수 있으므로 채택하지 않는다.
3. **사용자에게 수동 종료/새 터미널/재로그인 요구**: 이미 반복 보고된 불편을 유지하므로 채택하지 않는다.

추천안은 기존에 사용자가 선택한 “공통 서버 전환·같은 창/대화 유지”와 “세션별 계정 교체”를 함께 만족시키기 위한 구현자 제안이다. 새 의존성과 Codex 포크는 도입하지 않는다.

## 기능 요구

### 1. 계정 확인

- 확인은 읽기 전용이며 로그인/로그아웃, 세션 중단, Goal 일시정지, 데몬 시작/재시작, 자동 전환을 실행하지 않는다. 자동 전환이 꺼져 있어도 가능하다.
- 현재 저장된 로그인, 연결 서버 계정, 마지막 성공 시각과 조회 불가를 구분한다. 원하는 새 계정과 실제 계정의 같음을 확인하기 전에는 변경 완료라 표시하지 않는다.
- 기존 임시 app-server 메타데이터 조회는 시작만으로 읽기 전용이라고 가정하지 않는다. 인증 갱신/선택 변경·Goal 변경이 없음을 소유 시험 홈에서 검사하고, 조회용 상태 초기화와 실제 인증 변경을 구분한다. 현재 서버를 읽는 공식 API를 우선한다.
- 실제 실행 중인 native CLI의 검증된 절대 경로를 우선한다. npm/Homebrew 탐색이 필요한 경우에만 셸 환경을 한 번 확보해 재사용하며 홈/실행 파일 변경과 취소를 반영한다.
- 같은 홈의 동시 조회는 합치고 조회 대기와 로그인/전환의 변경 잠금을 분리한다. 마지막 성공 값은 오래된 값임을 표시한 채 유지하며 늦은 다른 홈 응답은 버린다.
- 목표: 이미 검증한 native CLI 경로의 조회에 반복 로그인 셸 실행 0회. 다른 Mac의 실제 측정에서 현행 셸 초기화 비용을 제거했는지 검증한다.

### 2. 계정 변경

- 변경 대상은 “공유 계정 N개 세션” 또는 선택된 독립 그룹으로 고정하고 영향을 받는 대화/세션 수를 미리 표시한다.
- 이미 저장된 계정 선택과 새 브라우저 로그인을 제공한다. 계정/워크스페이스 식별자는 노출하지 않고 내부 검증에만 사용하며 토큰을 복사/로그/진단 내보내기에 포함하지 않는다.
- 저장 계정은 login sessionId와 workspace accountId의 쌍으로 선택하고 계정·워크스페이스 이름을 함께 표시한다. accountId를 사용자 ID로 취급하지 않는다. allowBrowserLogin 정책을 명시하고 SSO가 필요해 auth_url/login_id가 반환되면 공식 인증 대기 단계로 전환한다. 로그인 ID와 의도한 계정/워크스페이스 쌍을 저널에 보관하고 완료 알림 뒤 실제 계정을 검증한다.
- 공식 accountSession/switch로 대상 계정을 선택하는 경로는 실제 0.166 시험에서 지원 여부/영향을 확인한 뒤 사용한다. API 미지원/명시적 거절은 표시하고, 전달이 불명확하면 다른 방식으로 자동 재전송하지 않는다.
- 새 로그인 인증 성공, 서버 계정 반영, 선택 대화 연결, 중단 작업 재개를 별도 상태로 표시한다.
- 작업/Goal을 순차적으로 중단하고 대기 결과를 관찰한다. 원래 대기/중지/초안/질문은 보존하고 이번 전환으로 중단한 작업만 한 번 이어간다.
- 동일 홈에서 이미 진행 중인 변경은 상태를 조회해 이어가고 중복 예약을 만들지 않는다. 취소/앱 재시작/타임아웃은 기존 영속 저널과 원본 신원 재검증을 따른다.

### 3. 세션 통합과 분리

- 계정 그룹은 canonical CODEX_HOME과 실제 서버 연결 증거로 구분한다. 기존 사용자 홈과 자동 생성한 전용 홈을 함께 다룬다. 경로/사용자명/아키텍처를 개발 Mac에 고정하지 않는다.
- 한 개 또는 여러 선택 세션을 기존 그룹으로 통합하거나 새 독립 그룹으로 분리할 수 있다. 선택하지 않은 세션은 중단/계정 변경/재실행하지 않는다.
- **공유 계정 변경과 선택 세션 이동은 별도 작업이다.** 전자는 해당 서버에 붙은 전체 클라이언트에 영향을 주며, 후자는 현재 전체 대화를 열거/재시작하는 coordinator를 그대로 사용하지 않는다. 선택 이동에서는 양쪽 공유 데몬을 재시작하지 않는다. 선택 단위는 터미널 클라이언트와 그 클라이언트의 영향을 받는 모든 대화/자식 스레드이며, 미선택 클라이언트도 같은 대화를 소유하면 먼저 충돌로 표시하고 이동을 실행하지 않는다.
- 새 그룹은 앱 전용 사용자 소유 디렉터리에 생성하고 그 홈에서 로그인한다. 기존 auth.json/키체인/API 키를 임의 복사하지 않는다.
- 대상 로그인과 서버 준비가 확인된 뒤 이동을 예약한다. 이동 전 원본의 PID/시작/TTY/대화 ID/계정/Goal과 목적지의 상태를 다시 검증한다.
- 같은 창/탭의 기존 복구 흐름을 사용하며 원본 셸이 없으면 사용자가 이미 선택한 같은 창의 복구 탭 교체를 사용한다.
- 다른 홈으로 옮길 때도 대화 UUID, 보존된 대화 이력, 원래 설정, Goal 목표/상태/instance/토큰 예산/누적 사용량/시간을 보존한다. 목표를 새로 생성해 사용량을 초기화하거나 새 대화 포크로 성공을 대체하지 않는다.
- 원래 설정은 확인 가능한 model/provider, reasoning, service tier, approval/reviewer/sandbox, 작업 폴더·workspace roots, instructions와 plugin 구성을 포함한다. 인증이 필요한 도구는 자격 증명을 복사하지 않고 목적지에서 사용할 수 있는지를 원본 중단 전에 확인한다. 읽을 수 없거나 재현할 수 없는 설정은 조용히 기본값으로 대체하지 않는다.
- 초안·질문·독립 백그라운드 작업이 있으면 원본을 그대로 유지하고 이동 가능 상태까지 기다린다. 종료한 임의 프로세스를 자동 복원한다고 약속하지 않는다. 공식 재개 가능한 상태를 입증한 작업만 이동/이어가기에 포함한다.
- 먼저 설치된 공식 CLI의 rollout path resume/import 가능성과 Goal 보존을 소유 시험 홈/세션에서 검증한다. Goal 메타데이터에 공식 이관 기능이 없으면 0.166의 확인한 스키마에 한정한 단일 대화 이관을 검토하며, 원본은 그대로 보관하고 목적지 충돌을 거절한다. 검증되지 않은 스키마나 변경된 원본에는 쓰지 않는다. 이 선택은 검증 결과와 함께 설계에 갱신한다.
- 이관은 **구현 가능성 검증을 통과하기 전 사용하지 않는다.** thread/resume의 path는 unstable이고 비실행 threadId를 무시할 수 있다. history 필드는 cloud 전용이므로 사용하지 않는다. 소유 시험에서 같은 UUID·전체 이력·독립된 목적지 rollout·유효 설정·정확한 Goal 메타데이터를 입증해야 한다. source rollout path를 목적지의 쓰기 파일로 사용하지 않는다. 이 검증의 실패는 전체 목표의 미완료로 남기며, 포크/Goal 재생성으로 성공 기준을 바꾸지 않는다.
- 원본과 목적지에서 같은 대화가 동시에 실행/기록되지 않아야 한다. 마지막 연결이 확인되기 전 원본 데이터·프로필을 삭제하지 않는다.
- 두 홈의 canonical 신원과 실제 소켓/데몬/인증 저장소 격리를 각각 검증한다. 경로가 다르다는 이유만으로 계정 격리라고 표시하지 않는다. 소유 두 홈에서 한쪽 로그인/전환이 다른 쪽 인증·실행을 바꾸지 않는지 검사한다.
- 이관 저널은 양쪽 홈/서버 신원, 원본 cohort, 대화별 소유권, import fingerprint, 단일 writer 잠금과 commit 경계를 영속화한다. 홈 잠금은 정렬된 순서로 획득한다. 원본 클라이언트/writer 종료와 마지막 이력/Goal 사용량 flush를 확인한 뒤 목적지를 실행한다. unsubscribe 응답만으로 unload/정리가 끝났다고 간주하지 않는다. 실행 결과가 불명확하면 조회만 수행하며 자동 재실행/되돌림을 하지 않는다.
- 그룹/대화 목적지 매핑을 저장해 앱 재시작과 저장 복원에서도 이동 완료 대화를 이전 홈으로 다시 실행하지 않는다. 외부에서 원본 대화를 다시 열거나 대화/파일이 바뀌면 자동 동작을 보류하고 실제 소유권을 다시 확인한다.
- 통합 후 비어 있는 전용 홈의 제거는 별도 사용자 동작으로 둔다. 사용자가 만든 홈/인증/데몬은 자동 삭제하지 않는다.

## 화면과 상호작용

기존 SwiftUI 시스템 서체/의미 색/SF Symbols/24pt 여백/600×660 계정 창과 세션 상세 컴포넌트를 재사용한다. 주 화면은 현재 계정·조회 시각 → 계정 확인/변경 → 세션 그룹과 선택 → 통합/분리 진행 순서다.

- 읽기 확인은 별도 로딩 표시이며 다른 그룹의 로그인 조작을 잠그지 않는다. 동일 그룹의 변경 중에는 영향을 받는 변경 버튼만 비활성화한다.
- 선택 체크·전체/일부 선택·대상 그룹 선택과 변경될 세션 수를 표시한다. 단순 버튼 나열 대신 계정/그룹별 목록과 진행 단계를 제공한다.
- 로딩·없음·로그인 전·현재/저장 계정 불일치·권한 거절·미지원·확인 불가·오래된 값·취소·완료·긴 이메일/프로젝트/홈·좁은 창/스크롤을 다룬다.
- 기능 검증과 네이티브 밝음/어두움 시각 검증을 분리한다. 웹 변경을 포함하는 경우에만 390×844/768×1024/1440×900을 검사한다.
- 원격 진단에는 로그인/연결/이관 단계와 시간·오류 분류만 허용 목록으로 제공하며 토큰·계정 식별자·대화/Goal 본문을 내보내지 않는다.

## 검증과 완료 조건

- 기존 계정/Goal/연결 검사 기준을 유지한다. 재현 실패 → 수정 → 통과 증거를 남긴다.
- 느린 초기 셸·native/npm 경로·다른 홈/사용자명·동시 조회·취소/잠자기/재시작·오래된 응답·바뀐 서버/프로세스·지원 안 되는 API·중복 요청을 검증한다.
- 서로 다른 계정 그룹의 선택 세션 통합/분리, 같은 프로젝트의 여러 창, 같은 대화 충돌, 원본 없는 셸, 진행 Goal/중지 Goal/초안/질문/배경 작업을 검증한다. 선택하지 않은 세션의 PID/계정/Goal을 보존한다.
- 실제 Codex의 소유 시험 홈/PTY/공통 서버에서 대화와 Goal 누적 사용량을 보존한 왕복 통합/분리 및 재개를 확인한다. 가짜 서비스만으로 실제 계정 이관 성공을 주장하지 않는다.

## Goal 보존 저장소의 실제 검증 · 2026-11-04

실제 설치된 0.166과 소유 홈 세 개에서 비어 있지 않은 같은 UUID 대화의 A→B→C 연속 이관, 공개 goal/get, 정확한 Goal instance/예산1234/누적토큰37/시간19초/밀리초 DB 행을 비교해 통과했다. 모델·공급자·작업 경로·승인/샌드박스 등 실제 응답 설정과 user/assistant 이력도 연속 비교했다. 대상의 무관한 Goal과 공유 서버 프로세스는 유지됐다. 자동 이어가기 보류 행은 네이티브 재개 후에도 남았다. 이는 이전 A 홈을 재사용하는 A→B→A 증거가 아니며, 기본값이 아닌 reasoning/tier/instruction/plugin 설정에는 별도 검증이 필요하다.

추가로 `thread/unsubscribe` 성공 응답만으로는 선택 대화가 메모리에서 내려가지 않는 실패를 재현했다. 소유 대화에 명시적인 `thread/archive`를 적용한 뒤 loaded 목록에서 실제 제거되고 rollout FD가 닫힌 것을 확인해야 공유 서버를 재시작하지 않고 다음 이관을 진행할 수 있었다. 이 공식 보관 동작은 원본 삭제가 아니며 저널에 기록해야 한다. 보관 명령의 전달이 불명확하면 재전송하지 말고 실제 보관·loaded·writer 상태를 조회한다.

## 두 홈 저널과 기존 홈 재사용의 검증 상태 · 2026-11-04

내부 `CodexMigrationJournal`은 전용 AuditStore 연결의 중앙 CAS 리비전과 두 홈의 0600 사본을 사용한다. 물리 홈 신원으로 중복 별칭을 거절하고 파일 신원 순서의 비차단 flock을 획득한다. 0700 폴더와 nofollow/openat 파일 접근, 임시 파일 동기화·원자적 rename·폴더 동기화를 적용한다. SQLite의 FULL/fullfsync 동기화 조건도 요청하고 다시 읽어 확인한다([공식 SQLite 설명](https://www.sqlite.org/pragma.html#pragma_fullfsync)). 조회 실패를 ‘기록 없음’으로 바꾸지 않으며, 서로 다른 사본은 원래 리비전·digest 체인에서 한 단계만 뒤진 경우에 같은 예약으로 복구한다. 이 저장소 자체는 세션 명령을 전송하지 않는다.

저널 계약 8개가 통과했다. 다른 프로필의 중복 요청 거절 후 남는 잠금과, 새로운 활성 요청 때문에 과거 완료 기록 조회가 실패하는 문제를 각각 실패 재현 후 수정했다. 실제 시험 프로세스의 `_exit`를 중앙 기록 직후·첫 미러 직후·전체 동기화 직후에 실행한 3개 경우도 같은 attempted 예약 복구, 외부 요청 차단, terminal 이후 해제를 확인했다. 이는 파일/프로세스 복구 증거이며 조정기의 네이티브 명령 재전송 방지나 전원 손실 전체를 검증했다는 뜻은 아니다.

`--return-original-home` 실제 시험은 A→B→A에서 의도적으로 실패한다. A에는 과거 37토큰 Goal이 남아 있고 B의 최신 Goal은 73토큰·29초다. insert-only 저장소는 임의 충돌을 덮어쓰지 않는다. 다음 조정기는 해당 A 슬롯이 이전 이관에서 보관된 원본이라는 terminal 저널, 정확한 과거 Goal/rollout fingerprint, 현재 writer 부재와 현재 소유 홈을 검증해야 한다. 그 증명 아래에서만 과거 복사본을 별도로 보존하고 조건부 CAS 교체를 허용한다. B에서 Goal을 지운 경우에도 오래된 A Goal을 되살리지 않아야 한다. 새 홈을 계속 만들어 이 요구를 우회하지 않는다.

기존 ‘현재 로그인으로 세션 재연결’의 실제 Goal 중단·한 번의 재개도 별도 소유 TUI/관리형 데몬에서 확인해야 한다. 계정 메타데이터를 합성한 시험은 실제 인증·SSO 전환 완료의 증거로 사용하지 않는다. 이후 선택 cohort 검증, 명령별 reserved/attempted/verified 구분, 현재 소유권 매핑과 사용자 UI 연결이 남아 있다. 운영 제품은 0.2.250을 유지한다.

## 선택 이관 준비 조정기의 범위 · 2026-11-04

내부 `CodexSessionMigrationCoordinator`는 검증한 두 물리 홈·서버·소켓·인증 저장소와 계정/로그인 세션/워크스페이스, 선택 클라이언트의 PID·시작·TTY 및 모든 자식 대화를 예약한다. 미선택 클라이언트가 같은 대화를 쓰거나 초안·질문·대기 입력·독립 작업·보존 불가능한 설정이 있으면 예약하지 않는다. 같은 계정이어도 독립 홈은 허용하지만 같은 인증 백엔드를 다른 홈으로 위장한 제안은 거절한다.

## Goal 부재 상태의 보존 근거 · 2026-11-04

왕복 이관에서 Goal을 지웠다는 사실도 정확한 원본 상태다. 내부
`CodexGoalTransferSlot`은 물리 홈과 홈 디렉터리 신원, goals DB 파일 신원,
검증한 스키마, 대화 ID, 존재할 경우의 정확한 Goal 행, 이어가기 보류 값과
digest를 함께 기록한다. 행이 없어도 이 기록을 반환한다. DB 없음·조회 실패·
미지원 스키마·고아 보류 행을 Goal 부재로 바꾸지 않는다. 다시 검증할 때는
같은 원본을 재조회하므로 이후 생성된 Goal·변경된 보류·교체된 DB/홈과
혼동하지 않는다.

기존 insert-only 복원용 스냅샷도 홈 디렉터리 신원을 포함한 내부 형식
2로 변경했다. 같은 DB inode를 새 홈 디렉터리로 옮긴 뒤 과거 스냅샷으로
복원을 요청하는 사례가 실제로 잘못 허용됐으며, 새 형식은 원본 재조회에서
이를 거절한다. 내부 형식 1을 새 권한으로 자동 승격하지 않는다. 이는
Codex 자체의 goals DB 스키마 버전을 변경하는 작업이 아니다.

이 기록은 과거 A 슬롯을 덮어쓰거나 지울 권한이 아니다. A→B→A에서 현재
B의 부재 기록을 보존하려면 이전 이관의 terminal 소유권 영수증, 현재
소유자 매핑, 정확한 과거 A Goal/rollout fingerprint, writer 부재와 동기화된
백업을 먼저 확인해야 한다. 그 뒤 조건부 교체를 시도하기 전에 현재 이관
저널에 attempted를 영속화하고, 결과가 불명확하면 실제 상태를 조회한다.
이 전제와 복구 검증이 없는 임의 충돌은 계속 거절한다. 슬롯 캡처만으로
왕복 이관 완료를 주장하지 않는다.

실제 소유 세 홈의 기존 이관 시험에 `--check-cleared-slot`을 추가했다.
정확한 Goal/이력 보존을 확인한 뒤 목적지에서 공식 `thread/goal/clear`를
호출하고 공개 조회와 슬롯 기록으로 부재를 확인한다. 같은 대화를 공식
재개한 후에도 부재가 유지되고 무관한 Goal은 그대로인지 확인한다. 이
시험은 이전 A 홈의 오래된 Goal을 조건부로 지우는 검증과 별개다.

## 완료 저널과 현재 소유 홈의 원자적 저장 · 2026-11-04

내부 `CodexMigrationJournal.complete`는 선택한 대화별 이전 소유권 전체를
비교한 뒤 완료 기록과 모든 새 소유권 행을 전용 AuditStore의 한 트랜잭션에
저장한다. 대화 소유권은 대화 ID·물리 홈 신원·소유권 리비전·완료 저널 ID와
digest로 묶인다. 새 소유권이 포함된 완료 저널은 내부 형식 2이며, 기존
형식 1의 예약·취소 기록은 소유권을 새로 부여하지 않는다. SQLite 변경 중
한 대화라도 실패하면 중앙 완료 기록과 앞서 변경한 대화들도 롤백한다.

중앙 저장 직후 사본 동기화가 실패하면 소유권 행은 DB에 존재할 수 있다.
하지만 `owner`는 양쪽 홈 사본이 같은 terminal 기록과 일치할 때만 이를
반환한다. 재시작 후 같은 기록을 복구해도 소유권 리비전을 또 올리지 않는다.
소유권 테이블이 없어졌는데 완료 이력이 있거나, 해당 소유권 행만 사라졌는데
저널에 같은 대화의 완료 이력이 있으면 빈 초기 상태로 취급하지 않는다.
이 확인은 누락된 행의 예외 경로에서 이력을 조회하며, 정상 소유권 조회는
기본 키로 해당 행과 연결된 완료 기록을 읽는다.

8개 실제 SQLite/파일 계약 검사가 메타데이터의 A→B→A 리비전, B→C 이후
오래된 B 영수증 거절, 미선택 대화 유지, 배치 롤백, 재시작 사본 복구와
유실/오염 거절을 확인했다. 별도 프로세스를 `_exit`로 종료하는 시험은
중앙 직후·첫 사본 직후·전체 동기화 직후의 3개 기존 attempted 경계와
3개 새 ownership 완료 경계를 확인했다. 새 완료 경계에서 중앙 소유권과
영수증이 함께 남고, 사본 복구 전에는 조회를 거절하며, 복구 후에도 같은
소유권 리비전인 것을 확인했다. 네이티브 세션 명령은 0회다.

이는 현재 소유자 매핑의 저장 계약이다. `complete`의 호출자는 실제 선택
cohort와 원본 종료·목적지 연결을 먼저 검증해야 하며, 현재 제품에는 그런
네이티브 호출 경로가 없다. 형식에 맞는 합성 완료 payload는 그 검증을
대신하지 않는다. 과거 Goal/rollout 영수증과 백업, 조건부 교체, 실제
A→B→A 보존/재개는 여전히 별도 미완료다. 현재 조회는 완료 기록의 양쪽 홈을
유지하는 계약이며, 사용자 동작으로 빈 그룹을 제거할 때의 영수증 보관
정책도 실제 삭제 UI를 연결하기 전에 정해야 한다.

## 비기본 설정의 실제 이관 검증 · 2026-11-04

소유 시험에 `--check-settings`를 추가했다. 원본에 reasoning `high`, 서비스
등급 `flex`, 별도 base/developer 지시문, 비어 있지 않은 비활성 플러그인 ID
목록과 cwd와 다른 선택 workspace root를 설정한다. 세 홈의 기존 정확한
Goal·이력 이관 이후 목적지 응답의 reasoning/tier/plugin 목록/root를 비교한다.
이관 후 합성 추론도 한 번 실행해 원본과 목적지의 로컬 Responses 요청에서
reasoning `high`, `service_tier=flex`와 실제 system/developer 역할의 두 지시문을
확인한다. 단순히 과거 사용자 메시지에 지시문 문자열이 남아 있는 것을
성공으로 취급하지 않는다. 두 추론 모두 loopback 공급자이며 인증은 없다.

원본에서 `priority`를 요청한 첫 시험은 이관 전에 응답의 serviceTier가 null,
추론 요청에 service_tier가 없는 상태로 실패했다. 따라서 이 결과는 이관
손실로 분류하지 않는다. 별도 권한 없이 허용되는 것으로 소스에 표시된
`flex`로 비기본 등급의 저장·재개·실제 요청 반영을 검증했다. `priority`의
실제 계정/모델 지원과 보존은 이 시험으로 입증되지 않았다.

이 검증은 비활성 플러그인 **목록**의 보존을 확인한다. 실제 설치된 플러그인의
도구·지시문·인증을 목적지에서 실행하거나, 모든 설정 조합의 보존을 검증한
것은 아니다. 그 가용성 사전 확인과 실제 사용자 인증, A→B→A의 기존 홈
재사용은 별도 미완료로 유지한다. 이 시험 옵션은 제품 이관 경로를 활성화하지
않는다.

## 구현자 검토 · 2026-11-04

독립 읽기 전용 검토에서 cross-home 이관의 구현 가능성, 공유 계정 변경/선택 이관의 영향 범위 차이, 양방향 영속 저널/단일 writer, 계정+워크스페이스+SSO, 초안/하위 작업/설정 보존, 실제 인증 격리와 순수 조회 입증을 선행 조건으로 지적했다. 위 요구에 반영했다. 디렉터리/잠금/캐시 표현은 구현자가 정하며 추가 사용자 선택은 필요하지 않았다. 확인되지 않은 이관 기능을 이미 가능하다고 표시하지 않는다.
