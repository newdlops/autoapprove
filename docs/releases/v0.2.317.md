# AutoApprove 0.2.317 · build 344

세션 ID 조회와 MCP 연결의 일시적인 실패를 줄였습니다. Codex·Claude의 긴
승인창 수정(0.2.315·0.2.316)도 포함합니다.

MCP의 긴 도구 요청이 연결 확인용 `ping`까지 막던 문제를 격리된 실제 stdio
중계기로 재현했습니다. 수정 전 약 4초의 도구 대기가 끝나야 ping도 응답했습니다.
수정 후 같은 대기 중에 ping과 도구 목록이 먼저 응답하며, 독립 조회도 긴 변경
요청 뒤에서 기다리지 않습니다. 조회는 최대 4개씩 처리하고 전체 도구 대기는
16개로 제한합니다. 상태를 바꾸는 요청의 접수 순서는 유지합니다.

앱의 Unix 리스너가 교체되는 짧은 구간에는 아직 요청을 보내지 않은 연결 실패만
총 1.5초 범위의 대기 간격으로 다시 연결합니다. 서버가 요청을 받았을 수 있는데
응답이 유실된 경우에는 자동 재전송하지 않습니다. 연결 시작에도 제한시간을
적용하며 외부 네트워크를 사용하지 않습니다.

Claude 세션 파일을 읽는 도중 파일이 교체되면 다시 읽습니다. 일시적인 부분
읽기나 해석 실패를 캐시에 남기지 않고, 바뀐 파일의 ID로 이전 내용을 발표하지
않습니다. Codex는 열린 새 기록의 첫 줄이 아직 완성되지 않았을 때만 짧게
재확인합니다. 여러 대화가 동시에 잡히거나 프로세스가 바뀐 경우에는 재시도로
임의의 대화를 선택하지 않습니다. 기록 파일이 없는 관리형 클라이언트에는
매번 재시도 지연을 추가하지 않습니다.

동시에 들어온 그룹 세션 조회는 진행 중인 한 번의 관측을 공유합니다. 프로세스
전후 확인은 유지하고, 그 관측이 끝난 뒤의 새 조회는 다시 읽습니다. 중복 스캔과
동시 그룹 갱신 충돌을 줄이며 지난 관측 결과를 계속 재사용하지 않습니다.

검증: `scripts/mcp-resilience-check.mjs`는 격리된 Unix 리스너와 실제 stdio
중계기로 긴 요청 중 ping·독립 조회 응답, 과부하 제한, 리스너 재시작, 응답 유실
시 중복 전송 방지와 연결 소유자 유지를 확인합니다. 최종 디버그 검사에서 ping은
11ms에 응답했습니다. 기존 프레임 검사 15개, 요청별 대화 식별 검사 5개,
그룹 호출자 격리·재연결 검사도 통과했습니다. 세션 파일 교체·부분 읽기,
Codex 헤더 지연·모호한 대화·PID 교체, 동시 조회 공유와 후속 조회의 신선도를
별도 회귀 검사에 포함했습니다. 사용자 터미널에는 시험 입력을 보내지 않았습니다.

전체 디버그 검사 309개가 통과했습니다. IP 네트워크를 차단한 샌드박스에서도
그룹 검사 39개와 실제 MCP 격리·재연결 검사가 통과했습니다. Unix 소켓 자체를
차단한 검사에서는 권한 차단을 정확히 보고하며 재전송하지 않았습니다.

앱의 세션 ID 조회 수정은 새 앱을 실행하면 적용됩니다. 이미 실행 중인 stdio
중계기의 코드는 앱 파일 교체만으로 바뀌지 않으므로, MCP 중계기 수정은 연결을
다시 열어 새 실행 파일을 사용한 시점부터 적용됩니다.

최종 배포 빌드의 전체 회귀 검사 278개와 실제 배포 중계기의 안정성 검사도
통과했습니다.
