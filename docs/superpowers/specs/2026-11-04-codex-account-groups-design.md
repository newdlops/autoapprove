# Codex 계정 확인·변경과 세션 그룹 통합·분리 설계

날짜: 2026-11-04
상태: 독립 구현자 검토 반영 · 구현 전 설계 확인
목표 원문: “코덱스 로그인 확인과 로그인 계정 변경 각각 독립적인 세션의 통합과 분리를 개선하고 속도와 안정성을 향상시키자.”

## 사용자 요구와 현재 증거

- 사용자는 로그인 변경을 열린 세션에 반영하고, 특정 세션은 별도 계정으로 로그인할 수 있기를 요청했다. 창·탭·대화와 Goal을 보존하고 작업은 순차 중단한 뒤 실제 연결을 검증해야 한다.
- 다른 Apple Silicon Mac의 별도 진단 셸에서 CLI login status 0.17초, --version 0.08초, daemon version 0.25초, 새 zsh -lic 초기화 4.22초를 관찰했다. 현재 ChatGPT 로그인, daemon 0.166.0 running, daemon_auto_start=true, 원본 세션 3개 유지였다. 실제 다른 계정의 브라우저 인증은 아직 재현하지 않았다.
- 0.2.249는 서버 조회의 각 명령에 새 로그인 셸을 사용하고, 진단은 6초 제한이다. 네이티브 계정 UI의 loading은 서버 조회와 로그인 조작을 함께 막는다.
- 세션별 계정 화면은 공유 세션 수를 표시하지만 실제 분리/통합 동작은 없다. 현재 로그인 확인 버튼은 자동 전환과 묶여 있어 순수 조회로 볼 수 없다.
- 설치된 0.166.0의 생성 스키마에 accountSession/list와 accountSession/switch가 있다. thread/start/resume에는 명시적인 계정별 바인딩 필드가 확인되지 않았다. 이 버전의 실제 프로토콜로 검증하고 미래 버전을 추측하지 않는다.

## 접근 방식

### 0.166 계정 세션 API의 확인된 범위

정확한 소스 `6ff1e1ca3b30fc8b914720681fcf5fe62e95f856`의
`request_processors/account_processor/workspace_switching.rs`는
`accountSession/list`에 현재 관리형 로그인 한 개만 반환한다.
`accountSession/switch`의 `sessionId`는 그 로그인 신원이고 `accountId`는
그 로그인 안의 워크스페이스 신원이다. 이 API를 다른 ChatGPT 사용자의
저장 로그인 선택 기능으로 연결할 수 없다. 서로 다른 계정 선택은 별도
홈에 로그인한 그룹들을 선택하는 방식으로 구현한다. 아래의 저장 계정
요구는 그대로 유지하며, 계정 세션 API 하나만으로 충족됐다고 표시하지 않는다.

실제 0.166 소유 시험에서 A/B의 관리형 로그인 신원이 서로 다르고, 현재
워크스페이스 재선택은 같은 로그인·인증 파일·로드된 paused Goal을 유지하며,
B의 로그인 신원으로 A를 전환하려는 요청은 -32600으로 거절되는 것을 확인했다.
이 시험은 유효한 다른 워크스페이스 전환, 브라우저 SSO나 실제 인증을 증명하지 않는다.

1. **기존 관리형 서버 + 계정 그룹별 독립 CODEX_HOME (추천)**: 기존 순차 중단/연결 저널을 재사용한다. 같은 홈은 같은 계정을 공유하고, 독립 계정은 별도 홈/서버로 분리한다. 조회는 빠른 native CLI/공식 읽기 API로 분리한다. 지원되는 계정 전환 API는 실제 검증을 거쳐 사용한다.
2. **서버 하나에서 세션별 계정 덮어쓰기**: 현재 생성 스키마에서 세션별 인증 바인딩을 확인하지 못했다. 설정만으로 격리를 약속하면 다른 세션까지 계정이 바뀔 수 있으므로 채택하지 않는다.
3. **사용자에게 수동 종료/새 터미널/재로그인 요구**: 이미 반복 보고된 불편을 유지하므로 채택하지 않는다.

추천안은 기존에 사용자가 선택한 “공통 서버 전환·같은 창/대화 유지”와 “세션별 계정 교체”를 함께 만족시키기 위한 구현자 제안이다. 제품의 기본 실행 경로는 공식 Codex를 유지한다. 전체 TUI 소유권 API 부재가 확인돼 별도 소스 전용 조회 프로토타입을 준비하며, 기존 CLI 교체나 확장 배포를 자동으로 허용하지 않는다. 이 구현자 제안의 문구를 사용자 금지 지시로 취급해 격리된 소스 준비까지 막지 않는다.

## 기능 요구

### 1. 계정 확인

- 확인은 읽기 전용이며 로그인/로그아웃, 세션 중단, Goal 일시정지, 데몬 시작/재시작, 자동 전환을 실행하지 않는다. 자동 전환이 꺼져 있어도 가능하다.
- 현재 저장된 로그인, 연결 서버 계정, 마지막 성공 시각과 조회 불가를 구분한다. 원하는 새 계정과 실제 계정의 같음을 확인하기 전에는 변경 완료라 표시하지 않는다.
- 기존 임시 app-server 메타데이터 조회는 시작만으로 읽기 전용이라고 가정하지 않는다. 인증 갱신/선택 변경·Goal 변경이 없음을 소유 시험 홈에서 검사하고, 조회용 상태 초기화와 실제 인증 변경을 구분한다. 현재 서버를 읽는 공식 API를 우선한다.
- 실제 실행 중인 native CLI의 검증된 절대 경로를 우선한다. npm/Homebrew 탐색이 필요한 경우에만 셸 환경을 한 번 확보해 재사용하며 홈/실행 파일 변경과 취소를 반영한다.
- 같은 홈의 동시 조회는 합치고 조회 대기와 로그인/전환의 변경 잠금을 분리한다. 마지막 성공 값은 오래된 값임을 표시한 채 유지하며 늦은 다른 홈 응답은 버린다.
- 목표: 이미 검증한 native CLI 경로의 조회에 반복 로그인 셸 실행 0회. 다른 Mac의 실제 측정에서 현행 셸 초기화 비용을 제거했는지 검증한다.

### 2. 계정 변경

- 변경 대상은 “공유 계정 N개 세션” 또는 선택된 독립 그룹으로 고정하고 영향을 받는 대화/세션 수를 미리 표시한다.
- 이미 저장된 계정 선택과 새 브라우저 로그인을 제공한다. 계정/워크스페이스 식별자는 노출하지 않고 내부 검증에만 사용하며 토큰을 복사/로그/진단 내보내기에 포함하지 않는다.
- 저장 계정은 login sessionId와 workspace accountId의 쌍으로 선택하고 계정·워크스페이스 이름을 함께 표시한다. accountId를 사용자 ID로 취급하지 않는다. allowBrowserLogin 정책을 명시하고 SSO가 필요해 auth_url/login_id가 반환되면 공식 인증 대기 단계로 전환한다. 로그인 ID와 의도한 계정/워크스페이스 쌍을 저널에 보관하고 완료 알림 뒤 실제 계정을 검증한다.
- 공식 accountSession/switch로 대상 계정을 선택하는 경로는 실제 0.166 시험에서 지원 여부/영향을 확인한 뒤 사용한다. API 미지원/명시적 거절은 표시하고, 전달이 불명확하면 다른 방식으로 자동 재전송하지 않는다.
- 새 로그인 인증 성공, 서버 계정 반영, 선택 대화 연결, 중단 작업 재개를 별도 상태로 표시한다.
- 작업/Goal을 순차적으로 중단하고 대기 결과를 관찰한다. 원래 대기/중지/초안/질문은 보존하고 이번 전환으로 중단한 작업만 한 번 이어간다.
- 동일 홈에서 이미 진행 중인 변경은 상태를 조회해 이어가고 중복 예약을 만들지 않는다. 취소/앱 재시작/타임아웃은 기존 영속 저널과 원본 신원 재검증을 따른다.

### 3. 세션 통합과 분리

- 계정 그룹은 canonical CODEX_HOME과 실제 서버 연결 증거로 구분한다. 기존 사용자 홈과 자동 생성한 전용 홈을 함께 다룬다. 경로/사용자명/아키텍처를 개발 Mac에 고정하지 않는다.
- 한 개 또는 여러 선택 세션을 기존 그룹으로 통합하거나 새 독립 그룹으로 분리할 수 있다. 선택하지 않은 세션은 중단/계정 변경/재실행하지 않는다.
- **공유 계정 변경과 선택 세션 이동은 별도 작업이다.** 전자는 해당 서버에 붙은 전체 클라이언트에 영향을 주며, 후자는 현재 전체 대화를 열거/재시작하는 coordinator를 그대로 사용하지 않는다. 선택 이동에서는 양쪽 공유 데몬을 재시작하지 않는다. 선택 단위는 터미널 클라이언트와 그 클라이언트의 영향을 받는 모든 대화/자식 스레드이며, 미선택 클라이언트도 같은 대화를 소유하면 먼저 충돌로 표시하고 이동을 실행하지 않는다.
- 새 그룹은 앱 전용 사용자 소유 디렉터리에 생성하고 그 홈에서 로그인한다. 기존 auth.json/키체인/API 키를 임의 복사하지 않는다.
- 대상 로그인과 서버 준비가 확인된 뒤 이동을 예약한다. 이동 전 원본의 PID/시작/TTY/대화 ID/계정/Goal과 목적지의 상태를 다시 검증한다.
- 같은 창/탭의 기존 복구 흐름을 사용하며 원본 셸이 없으면 사용자가 이미 선택한 같은 창의 복구 탭 교체를 사용한다.
- 다른 홈으로 옮길 때도 대화 UUID, 보존된 대화 이력, 원래 설정, Goal 목표/상태/instance/토큰 예산/누적 사용량/시간을 보존한다. 목표를 새로 생성해 사용량을 초기화하거나 새 대화 포크로 성공을 대체하지 않는다.
- 원래 설정은 확인 가능한 model/provider, reasoning, service tier, approval/reviewer/sandbox, 작업 폴더·workspace roots, instructions와 plugin 구성을 포함한다. 인증이 필요한 도구는 자격 증명을 복사하지 않고 목적지에서 사용할 수 있는지를 원본 중단 전에 확인한다. 읽을 수 없거나 재현할 수 없는 설정은 조용히 기본값으로 대체하지 않는다.
- 초안·질문·독립 백그라운드 작업이 있으면 원본을 그대로 유지하고 이동 가능 상태까지 기다린다. 종료한 임의 프로세스를 자동 복원한다고 약속하지 않는다. 공식 재개 가능한 상태를 입증한 작업만 이동/이어가기에 포함한다.
- 먼저 설치된 공식 CLI의 rollout path resume/import 가능성과 Goal 보존을 소유 시험 홈/세션에서 검증한다. Goal 메타데이터에 공식 이관 기능이 없으면 0.166의 확인한 스키마에 한정한 단일 대화 이관을 검토하며, 원본은 그대로 보관하고 목적지 충돌을 거절한다. 검증되지 않은 스키마나 변경된 원본에는 쓰지 않는다. 이 선택은 검증 결과와 함께 설계에 갱신한다.
- 이관은 **구현 가능성 검증을 통과하기 전 사용하지 않는다.** thread/resume의 path는 unstable이고 비실행 threadId를 무시할 수 있다. history 필드는 cloud 전용이므로 사용하지 않는다. 소유 시험에서 같은 UUID·전체 이력·독립된 목적지 rollout·유효 설정·정확한 Goal 메타데이터를 입증해야 한다. source rollout path를 목적지의 쓰기 파일로 사용하지 않는다. 이 검증의 실패는 전체 목표의 미완료로 남기며, 포크/Goal 재생성으로 성공 기준을 바꾸지 않는다.
- 원본과 목적지에서 같은 대화가 동시에 실행/기록되지 않아야 한다. 마지막 연결이 확인되기 전 원본 데이터·프로필을 삭제하지 않는다.
- 두 홈의 canonical 신원과 실제 소켓/데몬/인증 저장소 격리를 각각 검증한다. 경로가 다르다는 이유만으로 계정 격리라고 표시하지 않는다. 소유 두 홈에서 한쪽 로그인/전환이 다른 쪽 인증·실행을 바꾸지 않는지 검사한다.
- 이관 저널은 양쪽 홈/서버 신원, 원본 cohort, 대화별 소유권, import fingerprint, 단일 writer 잠금과 commit 경계를 영속화한다. 홈 잠금은 정렬된 순서로 획득한다. 원본 클라이언트/writer 종료와 마지막 이력/Goal 사용량 flush를 확인한 뒤 목적지를 실행한다. unsubscribe 응답만으로 unload/정리가 끝났다고 간주하지 않는다. 실행 결과가 불명확하면 조회만 수행하며 자동 재실행/되돌림을 하지 않는다.
- 그룹/대화 목적지 매핑을 저장해 앱 재시작과 저장 복원에서도 이동 완료 대화를 이전 홈으로 다시 실행하지 않는다. 외부에서 원본 대화를 다시 열거나 대화/파일이 바뀌면 자동 동작을 보류하고 실제 소유권을 다시 확인한다.
- 통합 후 비어 있는 전용 홈의 제거는 별도 사용자 동작으로 둔다. 사용자가 만든 홈/인증/데몬은 자동 삭제하지 않는다.

## 화면과 상호작용

기존 SwiftUI 시스템 서체/의미 색/SF Symbols/24pt 여백/600×660 계정 창과 세션 상세 컴포넌트를 재사용한다. 주 화면은 현재 계정·조회 시각 → 계정 확인/변경 → 세션 그룹과 선택 → 통합/분리 진행 순서다.

- 읽기 확인은 별도 로딩 표시이며 다른 그룹의 로그인 조작을 잠그지 않는다. 동일 그룹의 변경 중에는 영향을 받는 변경 버튼만 비활성화한다.
- 선택 체크·전체/일부 선택·대상 그룹 선택과 변경될 세션 수를 표시한다. 단순 버튼 나열 대신 계정/그룹별 목록과 진행 단계를 제공한다.

## Goal 보존 저장소의 실제 검증 · 2026-11-04

실제 설치된 0.166과 소유 홈 세 개에서 비어 있지 않은 같은 UUID 대화의 A→B→C 연속 이관, 공개 goal/get, 정확한 Goal instance/예산1234/누적토큰37/시간19초/밀리초 DB 행을 비교해 통과했다. 모델·공급자·작업 경로·승인/샌드박스 등 실제 응답 설정과 user/assistant 이력도 연속 비교했다. 대상의 무관한 Goal과 공유 서버 프로세스는 유지됐다. 자동 이어가기 보류 행은 네이티브 재개 후에도 남았다. 이는 이전 A 홈을 재사용하는 A→B→A 증거가 아니며, 기본값이 아닌 reasoning/tier/instruction/plugin 설정에는 별도 검증이 필요하다.

추가로 `thread/unsubscribe` 성공 응답만으로는 선택 대화가 메모리에서 내려가지 않는 실패를 재현했다. 소유 대화에 명시적인 `thread/archive`를 적용한 뒤 loaded 목록에서 실제 제거되고 rollout FD가 닫힌 것을 확인해야 공유 서버를 재시작하지 않고 다음 이관을 진행할 수 있었다. 이 공식 보관 동작은 원본 삭제가 아니며 저널에 기록해야 한다. 보관 명령의 전달이 불명확하면 재전송하지 말고 실제 보관·loaded·writer 상태를 조회한다.

## 두 홈 저널과 기존 홈 재사용의 검증 상태 · 2026-11-04

내부 `CodexMigrationJournal`은 전용 AuditStore 연결의 중앙 CAS 리비전과 두 홈의 0600 사본을 사용한다. 물리 홈 신원으로 중복 별칭을 거절하고 파일 신원 순서의 비차단 flock을 획득한다. 0700 폴더와 nofollow/openat 파일 접근, 임시 파일 동기화·원자적 rename·폴더 동기화를 적용한다. SQLite의 FULL/fullfsync 동기화 조건도 요청하고 다시 읽어 확인한다([공식 SQLite 설명](https://www.sqlite.org/pragma.html#pragma_fullfsync)). 조회 실패를 ‘기록 없음’으로 바꾸지 않으며, 서로 다른 사본은 원래 리비전·digest 체인에서 한 단계만 뒤진 경우에 같은 예약으로 복구한다. 이 저장소 자체는 세션 명령을 전송하지 않는다.

저널 계약 8개가 통과했다. 다른 프로필의 중복 요청 거절 후 남는 잠금과, 새로운 활성 요청 때문에 과거 완료 기록 조회가 실패하는 문제를 각각 실패 재현 후 수정했다. 실제 시험 프로세스의 `_exit`를 중앙 기록 직후·첫 미러 직후·전체 동기화 직후에 실행한 3개 경우도 같은 attempted 예약 복구, 외부 요청 차단, terminal 이후 해제를 확인했다. 이는 파일/프로세스 복구 증거이며 조정기의 네이티브 명령 재전송 방지나 전원 손실 전체를 검증했다는 뜻은 아니다.

`--return-original-home` 실제 시험은 A→B→A에서 의도적으로 실패한다. A에는 과거 37토큰 Goal이 남아 있고 B의 최신 Goal은 73토큰·29초다. insert-only 저장소는 임의 충돌을 덮어쓰지 않는다. 다음 조정기는 해당 A 슬롯이 이전 이관에서 보관된 원본이라는 terminal 저널, 정확한 과거 Goal/rollout fingerprint, 현재 writer 부재와 현재 소유 홈을 검증해야 한다. 그 증명 아래에서만 과거 복사본을 별도로 보존하고 조건부 CAS 교체를 허용한다. B에서 Goal을 지운 경우에도 오래된 A Goal을 되살리지 않아야 한다. 새 홈을 계속 만들어 이 요구를 우회하지 않는다.

기존 ‘현재 로그인으로 세션 재연결’의 실제 Goal 중단·한 번의 재개도 별도 소유 TUI/관리형 데몬에서 확인해야 한다. 계정 메타데이터를 합성한 시험은 실제 인증·SSO 전환 완료의 증거로 사용하지 않는다. 이후 선택 cohort 검증, 명령별 reserved/attempted/verified 구분, 현재 소유권 매핑과 사용자 UI 연결이 남아 있다. 운영 제품은 0.2.250을 유지한다.

## Goal 부재 상태의 보존 근거 · 2026-11-04

왕복 이관에서 Goal을 지웠다는 사실도 정확한 원본 상태다. 내부
`CodexGoalTransferSlot`은 물리 홈과 홈 디렉터리 신원, goals DB 파일 신원,

소유자 매핑, 정확한 과거 A Goal/rollout fingerprint, writer 부재와 동기화된
백업을 먼저 확인해야 한다. 그 뒤 조건부 교체를 시도하기 전에 현재 이관
저널에 attempted를 영속화하고, 결과가 불명확하면 실제 상태를 조회한다.
이 전제와 복구 검증이 없는 임의 충돌은 계속 거절한다. 슬롯 캡처만으로
왕복 이관 완료를 주장하지 않는다.

실제 소유 세 홈의 기존 이관 시험에 `--check-cleared-slot`을 추가했다.
정확한 Goal/이력 보존을 확인한 뒤 목적지에서 공식 `thread/goal/clear`를
호출하고 공개 조회와 슬롯 기록으로 부재를 확인한다. 같은 대화를 공식
재개한 후에도 부재가 유지되고 무관한 Goal은 그대로인지 확인한다. 이
시험은 이전 A 홈의 오래된 Goal을 조건부로 지우는 검증과 별개다.

## 완료 저널과 현재 소유 홈의 원자적 저장 · 2026-11-04

내부 `CodexMigrationJournal.complete`는 선택한 대화별 이전 소유권 전체를
비교한 뒤 완료 기록과 모든 새 소유권 행을 전용 AuditStore의 한 트랜잭션에
저장한다. 대화 소유권은 대화 ID·물리 홈 신원·소유권 리비전·완료 저널 ID와
digest로 묶인다. 새 소유권이 포함된 완료 저널은 내부 형식 2이며, 기존
형식 1의 예약·취소 기록은 소유권을 새로 부여하지 않는다. SQLite 변경 중
한 대화라도 실패하면 중앙 완료 기록과 앞서 변경한 대화들도 롤백한다.

중앙 저장 직후 사본 동기화가 실패하면 소유권 행은 DB에 존재할 수 있다.
하지만 `owner`는 양쪽 홈 사본이 같은 terminal 기록과 일치할 때만 이를
반환한다. 재시작 후 같은 기록을 복구해도 소유권 리비전을 또 올리지 않는다.
소유권 테이블이 없어졌는데 완료 이력이 있거나, 해당 소유권 행만 사라졌는데
저널에 같은 대화의 완료 이력이 있으면 빈 초기 상태로 취급하지 않는다.
이 확인은 누락된 행의 예외 경로에서 이력을 조회하며, 정상 소유권 조회는
기본 키로 해당 행과 연결된 완료 기록을 읽는다.

8개 실제 SQLite/파일 계약 검사가 메타데이터의 A→B→A 리비전, B→C 이후
오래된 B 영수증 거절, 미선택 대화 유지, 배치 롤백, 재시작 사본 복구와
유실/오염 거절을 확인했다. 별도 프로세스를 `_exit`로 종료하는 시험은
중앙 직후·첫 사본 직후·전체 동기화 직후의 3개 기존 attempted 경계와
3개 새 ownership 완료 경계를 확인했다. 새 완료 경계에서 중앙 소유권과
영수증이 함께 남고, 사본 복구 전에는 조회를 거절하며, 복구 후에도 같은
소유권 리비전인 것을 확인했다. 네이티브 세션 명령은 0회다.

이는 현재 소유자 매핑의 저장 계약이다. `complete`의 호출자는 실제 선택
cohort와 원본 종료·목적지 연결을 먼저 검증해야 하며, 현재 제품에는 그런
네이티브 호출 경로가 없다. 형식에 맞는 합성 완료 payload는 그 검증을
대신하지 않는다. 과거 Goal/rollout 영수증과 백업, 조건부 교체, 실제
A→B→A 보존/재개는 여전히 별도 미완료다. 현재 조회는 완료 기록의 양쪽 홈을
유지하는 계약이며, 사용자 동작으로 빈 그룹을 제거할 때의 영수증 보관
정책도 실제 삭제 UI를 연결하기 전에 정해야 한다.

## 비기본 설정의 실제 이관 검증 · 2026-11-04

소유 시험에 `--check-settings`를 추가했다. 원본에 reasoning `high`, 서비스
등급 `flex`, 별도 base/developer 지시문, 비어 있지 않은 비활성 플러그인 ID
목록과 cwd와 다른 선택 workspace root를 설정한다. 세 홈의 기존 정확한
Goal·이력 이관 이후 목적지 응답의 reasoning/tier/plugin 목록/root를 비교한다.
이관 후 합성 추론도 한 번 실행해 원본과 목적지의 로컬 Responses 요청에서
reasoning `high`, `service_tier=flex`와 실제 system/developer 역할의 두 지시문을
확인한다. 단순히 과거 사용자 메시지에 지시문 문자열이 남아 있는 것을
성공으로 취급하지 않는다. 두 추론 모두 loopback 공급자이며 인증은 없다.

원본에서 `priority`를 요청한 첫 시험은 이관 전에 응답의 serviceTier가 null,
추론 요청에 service_tier가 없는 상태로 실패했다. 따라서 이 결과는 이관
손실로 분류하지 않는다. 별도 권한 없이 허용되는 것으로 소스에 표시된
`flex`로 비기본 등급의 저장·재개·실제 요청 반영을 검증했다. `priority`의
실제 계정/모델 지원과 보존은 이 시험으로 입증되지 않았다.

이 검증은 비활성 플러그인 **목록**의 보존을 확인한다. 실제 설치된 플러그인의
도구·지시문·인증을 목적지에서 실행하거나, 모든 설정 조합의 보존을 검증한
것은 아니다. 그 가용성 사전 확인과 실제 사용자 인증, A→B→A의 기존 홈
재사용은 별도 미완료로 유지한다. 이 시험 옵션은 제품 이관 경로를 활성화하지
않는다.

## 과거 원본의 영수증과 독립 백업 · 2026-11-04

`CodexMigrationRetirement`는 존재·부재를 포함한 정확한 Goal 슬롯과 보관된
rollout의 물리 홈/파일 신원·크기·수정 시각·SHA-256을 묶는다. 상대 경로의
모든 디렉터리를 nofollow로 열고 링크·hardlink·특수 파일·다른 소유자와
그룹/전체 쓰기 가능한 파일을 거절한다. 최대 256 MiB를 64 KiB씩 읽어
digest를 계산하고 읽기 전후 파일 상태와 Goal을 재검증한다. macOS의 /var
홈 별칭만 물리 경로에 맞추며 rollout 구성요소의 링크 금지는 완화하지 않는다.
안정된 archived 파일만으로 writer 종료가 입증되는 것은 아니다. 이 부분은
이후 네이티브 변경 경로에서 별도 관측해야 한다.

완료 소유권 변경에 이 과거 원본을 포함할 수 있다. 대화·홈과 이전 소유자가
출발 범위에 일치해야 한다. 반환 조회는 정확한 현재 소유자로 시작해 양쪽
사본이 일치하는 완료 소유권 저널을 digest로 따라간다. 추가 이동 후 오래된
소유자, 바뀐 Goal/이력, 과거 원본 증거가 없는 이력 구간은 거절한다.

`backupRetired`는 같은 두 홈의 잠금과 일치하는 nonterminal 예약을 요구한다.
과거 홈의 `.autoapprove-migrations/backups/<request>-<thread>`에 새 폴더를
만들고 이력의 독립 복사본과 JSON manifest를 배타적인 0600 파일로 저장해
파일/디렉터리를 동기화한다. manifest는 정확한 Goal/이력 증거, 현재 소유자,
예약 ID와 digest를 묶는다. 복사 후 원본도 다시 확인한다. 기존 또는 일부만
저장된 백업 폴더는 자동 채택하거나 덮어쓰지 않는다.

`verifyBackup`는 사용 직전 예약 리비전/digest·양쪽 사본·잠금·현재 소유자·
원본 영수증을 다시 확인하고 복사본 파일 신원/내용과 manifest를 검증한다.
예약이 변경되거나 취소되면 파일이 온전해도 교체 권한으로 사용하지 않는다.
향후 attempted 변경 단계는 이 백업과 원래 예약을 자체 영속 intent에
명시적으로 연결해야 한다. 현재 API는 그 단계나 불명확한 변경 재전송을
구현하지 않는다.

실제 소유 시험의 `--check-retirement`는 원본을 보관/종료하고 목적지의 같은
UUID·Goal·이력을 확인한 뒤 과거 원본 영수증과 백업을 만든다. 교체 없이
원본 Goal 행과 이력이 그대로인지 비교한다. 새 helper 프로세스에서도
백업을 검증하며, 취소된 백업 전용 예약은 교체 권한으로 사용할 수 없음을
확인한다. 시험의 합성 완료 payload는 사용자 세션용 네이티브 관측 제공자를
대신하지 않는다.

전체 Goal/rollout 반환, 최신 73토큰·29초를 보존하는 실제 A→B→A,
삭제된 Goal의 tombstone, 변경별 중간 종료/재전송 방지와 모든 네이티브
클라이언트·보조 대화 소유권은 미완료다. 제품 UI/IPC 연결은 없으며 설치된
제품은 0.2.251을 유지한다.

## 조건부 Goal 반환과 남은 실제 이력 경로 · 2026-11-04

내부 `CodexGoalReturn`은 백업·현재 소유자·원본 Goal 슬롯과 기존 예약
payload를 영속 intent에 묶는다. `prepare`는 백업 예약과 양쪽 사본을 확인하고
별도 리비전으로 저장한다. `apply`는 prepared에서만 시작하며 모든 사본에
attempted를 저장한 뒤 Goal DB에 접근한다. 이미 attempted 또는 verified인
요청을 다시 실행하지 않는다. Goal 값이 같으면 DB 쓰기 없이 unchanged를
저장한다.

실제 쓰기는 BEGIN IMMEDIATE 안에서 대상 DB/홈/스키마 신원과 정확한 과거
Goal/이어가기 보류 값을 비교한다. 일치할 때 선택 대화의 행만 최신 원본으로
교체한다. 원본 Goal이 없으면 과거 행과 보류도 삭제한다. 최신 행의 Goal
instance·누적 값·예산·밀리초 시각을 새 Goal 생성으로 대체하지 않는다.
커밋 전 예약·소유권·백업·원본을 다시 확인하고 실패하면 트랜잭션을 롤백한다.
원본 DB와 독립 백업은 그대로 유지한다.

`observe`는 DB/저널을 변경하지 않고 intended 값, 원래 값, 불명확한 값을
구분한다. 실제 DB 변경 뒤 verified 저널 저장이 끝나지 않은 경우에도
attempted intent를 읽어 결과만 확인한다. 이 관측은 Goal 저장소에 한정되며
네이티브 목적지 연결이나 최종 소유권을 승인하지 않는다. 소유자 매핑은
실제 대화 연결·이력 검증 뒤 별도 완료 단계에서만 갱신해야 한다.

8개 계약 검사는 정확한 37→73토큰/19→29초 교체, 삭제된 원본의 부재 유지,
attempted 이전/이후 DB 상태 조회와 실행 거절, 원본/대상/백업 변경 거절,
커밋 직전 권한 변경 롤백, 대상 잠금 실패 후 재실행 거절, 동일 값에서
Goal DB 쓰기 생략을 실제 SQLite로 확인했다. DB 변경 뒤 attempted 상태를
읽는 검사는 실제 저장소 쓰기와 새 조정기 객체를 사용했지만, 실제 프로세스
중단의 모든 Goal 변경 경계를 검증한 것은 아니다. 해당 경계별 시험은 남아 있다.

실제 `--return-original-home --check-retirement`는 Goal 저장소 반환까지
통과한 뒤 이력 재개에서 실패했다. 0.166은 기존 A의 paginated 대화를
`archived_sessions` 경로로 기억하므로, 새 `sessions` 경로를 지정한 재개에
`-32600` stale-path 오류를 반환했다. 이 오류는 소유 시험의 반환 경로에서
재현한 결과이며 과거 사용자 로그인 오류의 원인이 같다고 단정하지 않는다.

왕복 oracle는 B에서 추가 합성 대화를 만든 뒤 최신 이력이 늘었음을 확인한다.
기존 A 보관본을 경로 없이 다시 여는 것만으로는 이를 만족하지 못한다.
다음 구현은 정확한 과거 보관 파일의 독립 백업과 신원 비교를 유지하면서
최신 B 이력을 조건부로 반영하고, 네이티브 경로/보관 상태와 같은 UUID의
최신 이력을 재검증해야 한다. 이력이 확인되기 전 소유권 완료를 기록하거나
작업을 재개하지 않는다. 현재 전체 A→B→A 시험은 여전히 required RED이며,
제품 이관 경로는 연결하지 않았다.

정확한 0.166 소스의 `thread_unarchive_response`는 선택 root뿐 아니라
state DB의 spawned subtree도 보관 해제 대상으로 넘긴다. 공식 보관 해제를
사용하는 다음 단계에서도 양쪽 홈의 영향을 받는 하위 대화와 소유권을
먼저 확인해야 한다. root UUID 하나의 확인만으로 호출 범위를 축소해
가정하지 않는다. 현재 실제 시험에는 별도 spawned child가 없으며,
일반화된 unarchive 변경 경로는 전체 subtree 증거를 확보하기 전 연결하지 않는다.

후속 **별도 임시 프로토타입**에서는 이 경로의 실행 가능성을 확인했다.
원본과 독립 백업을 검증하고 Goal-only 반환이 끝난 뒤, 시험용 코드는 최신
B 이력을 기존 A 보관 위치에 복사하고 공식 `thread/unarchive`를 호출했다.
이후 공식 resume는 예상한 sessions 경로에서 같은 UUID를 열었다. B에서
새로 만든 user/assistant 이력 전체, 정확한 최신 Goal instance/73토큰/29초/
예산/밀리초 행, reasoning high·flex 등급·지시문·비활성 plugin 목록·별도
workspace root를 검증했고, 미선택 Goal과 공유 서버도 유지됐다. Goal을
지운 변형에서도 재개 뒤 goal/get이 null이며 과거 Goal은 되살아나지 않았다.
네이티브 연결 검증 뒤에만 시험의 소유자 매핑을 A로 완료했다.

이 프로토타입의 직접 파일 복사는 조건부 원자 교체·영속 attempted·중간
종료 복구를 구현하지 않는다. 따라서 제품 코드나 정규 성공 oracle로
승격하지 않았고, 소유 임시 홈에서의 가능성 증거로만 보관했다. 정규
`--return-original-home`은 안전한 이력 교체가 연결될 때까지 required RED를
유지한다. 실제 사용자 인증/TUI/Goal 중단·한 번의 재개는 이 익명 프로토콜
시험으로 입증되지 않는다.

## 저널에 연결된 보관 이력 반환 · 2026-11-04

후속 `CodexRolloutReturn`은 앞의 직접 복사 프로토타입을 정규 소유 시험에서
대체했다. Goal 반환이 검증된 같은 예약에서 현재 소유자의 정확한 Goal/이력
영수증을 추가한다. staging intent를 중앙과 두 사본에 저장한 뒤 독립 백업
폴더의 `replacement.jsonl`을 배타적인 0600 파일로 만든다. 64 KiB 스트리밍
복사 후 원본 지문과 복사본을 비교하고 파일/폴더를 동기화한다.

완전한 staging은 새 복사 없이 읽어서 prepared로 복구한다. 파일이 없거나
일부만 저장됐다면 복사를 다시 실행하거나 덮어쓰지 않는다. prepared에서만
교체를 시작하고 모든 저널 사본에 attempted를 저장한 뒤 원본/백업/Goal/
현재 소유자/예약과 정확한 보관 파일 신원을 다시 확인한다. 양쪽 디렉터리를
다시 열어 FD 신원을 비교한 뒤 같은 파일시스템의 rename으로 교체하고 두
폴더를 동기화한다. 교체 후 대상 inode와 digest가 staging과 같은지도 확인한다.
기존 Goal/이력의 독립 백업과 현재 소유자의 파일은 유지된다.

이는 네이티브 writer가 닫혔다는 전제 아래 신원/내용 비교 후 실행하는 원자
rename이다. 동시에 다른 writer가 임의로 파일을 바꾸는 상황에 대한 OS
수준 compare-and-swap은 아니다. 사용자 경로를 연결하기 전의 원본 종료/
flush·미선택 공유 writer·재진입 차단과 현재 소유권 검증을 생략할 수 없다.

조회는 실제 대상 inode/내용이 staging인지, 과거 보관본인지, 둘 다 아닌지를
분류하며 복사·rename·저널 쓰기를 하지 않는다. attempted 또는 verified
요청은 apply를 거절한다. Goal 값과 이력이 이미 같으면 각각 해당 DB/파일
교체 없이 unchanged를 기록할 수 있다. 이 단계는 보관 파일에서 끝나며
공식 보관 해제/재개와 최종 소유권 완료는 별도다.

6개 계약 검사는 정확한 원자 교체/독립 백업, 완성 staging 채택, 없음/부분
staging과 attempted 거절, 실제 rename 뒤 결과 조회, 변경된 원본/보관본/
백업/Goal 거절, 마지막 권한 확인 실패와 링크로 교체된 staging 거절을
확인했다. 별도 worker 프로세스를 `_exit`로 종료한 5개 경계는 staging intent
직후, 복사 완료 뒤 prepared 저장 전, attempted 저장 뒤 rename 전, 동기화된
rename 뒤 verified 저장 전, verified 저장 후다. 새 프로세스에서 완성본만
채택하고, rename 전후는 각각 notApplied/applied로 조회하면서 재실행을
거절했다. 이 worker는 실제 파일/SQLite/저널을 쓰지만 네이티브 Codex 프로세스는
사용하지 않는다. 각 경계는 실제 저장소 함수를 사용해 구성했으며 모든
전원 손실/동시 writer/네이티브 API 경계를 입증한 것은 아니다.

정규 `--return-original-home --check-retirement` 소유 네이티브 시험은 이제
새 반환 조정기로 보관 파일을 반영한 뒤 공식 보관 해제와 같은 UUID 재개를
검증한다. B-only 최신 대화와 정확한 73토큰/29초 Goal 및 비기본 설정,
미선택 Goal과 공유 서버가 유지됐다. Goal 삭제 변형도 최신 이력과 null
Goal을 유지했다. 새 소유자는 네이티브 전체 이력/Goal/설정 확인 뒤에만
완료했다. 위의 required RED 기록은 이전 Goal-only 단계의 결과이며 이
정규 왕복 경로에서 해소됐다.

이 시험의 unarchive는 spawned child가 없는 자체 생성 root를 대상으로
한 번 요청한다. 제품용 unarchive/resume의 영속 intent·불명확한 응답 복구,
양쪽 홈의 전체 영향 subtree, 실제 TUI/보조 대화 소유권과 실제 인증은
아직 연결/검증되지 않았다. 따라서 사용자 세션 통합/분리 완료나 전체
목표 달성으로 표시하지 않는다.

## 영속 보관 해제·재개와 검증 후 소유권 완료 · 2026-11-04

내부 `CodexNativeReturn`은 보관 파일 반환이 검증된 같은 저널에 서버/계정/
버전 신원과 영향 대화 전체의 원본 영수증, 목적지 파일 신원/경로, 기대
이력·설정 digest를 묶는다. 관측 제공자가 전체 영향 범위를 확인하지 못하거나
계획과 다른 ID가 나타나면 제어 요청을 보내지 않는다. 각 대화의 원본과
목적지 Goal 행/보류 값도 현재 상태에서 다시 비교한다.

보관 해제는 prepared→attempted를 모든 사본에 저장한 뒤 root에 한 번
요청한다. 응답이 불명확하면 실제 비보관 경로·같은 inode·언로드 상태를
조회해 다음 단계로 진행할 수 있지만 보관 해제를 다시 보내지 않는다.
이후 대화를 순서대로 prepared→attempted로 재개한다. 로드 상태뿐 아니라
최신 이력과 설정 digest가 일치해야 검증된다. 증거가 없으면 attempted에
남고 소유자는 원본으로 유지된다. 이미 로드된 다른 대화를 임의로 다시
재개하지 않는다. 모든 영향 대화가 검증된 뒤 최신 관측을 다시 확인하고
기존 원자적 완료/소유권 저장소로 전체를 함께 완료한다. 완료 상태는 제어
요청 없이 조회할 수 있으며 완료된 요청을 다시 실행하거나 커밋하지 않는다.

6개 계약 검사는 완료 전 소유권 유지, 보관 해제/재개가 반영된 뒤 응답 유실,
미반영 재개와 이력/설정 증거 부재, 서버/계정/버전/경로/영향 대화/대기 입력/
작업 상태 변경 거절, 같은 이력의 정상 복구, root+child의 순차 재개와 일괄
완료를 확인했다. 같은 이력에서 사용하지 않은 staging inode를 요구하던
문제와 완료 뒤 상태 조회 실패를 실제 3/5 실패에서 재현한 후 수정했다.
하위 대화 검사는 실제 파일/Goal/저널과 주입한 네이티브 서비스 관측을
사용하며 실제 Codex의 자식 생성/전체 클라이언트 탐색을 입증하지 않는다.

정규 소유 네이티브 시험은 Swift 조정기의 요청을 시험용 JSON-line bridge로
부모 Node의 실제 0.166 stdio 연결에 전달한다. 실제 account/read(null),
thread/read, loaded 목록과 생성한 서버 프로세스의 생존/세대 신원을 읽는다.
부모가 유일한 연결을 소유하고 모든 root를 직접 만들었으므로 해당 시험의
영향 범위는 구성으로 알려져 있다. 기존 사용자 TUI의 영향 범위를 이 방법으로
탐색했다는 뜻은 아니다. 실제 재개 응답의 설정 필드를 digest로 비교하며,
기존 미검증 완료 helper는 제거했다. 최종 소유권은 새 조정기만 완료한다.

`--crash-native-acks`는 실제 보관 해제 응답 직후와 실제 재개 응답 직후에
시험 제어 프로세스를 `_exit(52)`로 종료한다. 다음 프로세스는 기존 저널의
잠금을 복구하고 계획을 재사용해 실제 상태를 관측한다. 유일한 stdio 연결을
가진 시험 브로커는 살아 있으며 실제 재개 응답을 유지한다. 이 보존된 응답은
다른 입력자가 없는 해당 시험에서 설정 증거가 된다. 브로커까지 종료됐거나
다른 사용자 클라이언트가 설정을 바꿀 수 있는 상황의 현재 설정을 과거
응답만으로 입증하지 않는다. 그 경우 관측 제공자가 새 증거를 내놓지 못하면
조정기는 완료를 보류한다.

실제 제어 프로세스 2회 종료 후 보관 해제와 재개가 각각 1회만 전송됐고,
같은 UUID·최신 B-only 대화·정확한 73토큰/29초 Goal·비기본 설정·미선택
Goal/서버를 보존하며 완료했다. Goal 삭제 변형도 제어 프로세스 2회 종료와
각 제어 요청 1회 아래 최신 이력·설정과 null Goal을 유지하며 완료했다.
실제 사용자 인증/SSO, 기존 TUI의 모든 보조·offscreen·공유 구독과 초안,
원본 Goal 일시정지·한 번의 이어가기, 전체 그룹 UI/IPC 연결은 여전히 남아
있다. `completeScope`나 다른 신원 문자열을 채우는 것만으로 이 증거를
대체할 수 없으며 제품용 관측 제공자는 아직 연결하지 않았다.

## 0.167.1 원래 홈 반환 검증 · 2026-11-11

보관 이력 반환 조정기의 지원 버전에 정확한 0.167.1을 추가했다. 세션 이동의
준비 게이트나 사용자 UI는 이 변경으로 활성화되지 않는다. 시험 bridge는
실제로 실행한 CLI 버전을 전달하고, 저장 계획 복구와 새 관측에서 같은
버전인지 비교한다. 0.167.0, 0.167.2, 0.168.0은 허용하지 않는다.

독립 임시 홈과 로컬 합성 모델을 사용한 실제 0.167.1 A→B→A 시험이
통과했다. B에서 추가한 최신 대화와 같은 UUID, 정확한 Goal instance와
밀리초 행, 누적 73토큰·29초·예산 1234, 비기본 reasoning·service tier·
지시문·plugin 목록·workspace roots를 유지했다. 선택 writer의 닫힘과
flush를 확인했으며, 미선택 Goal과 공유 서버도 유지됐다. 실제 보관 해제와
재개 응답 직후 제어 프로세스를 각각 종료한 뒤 복구해도 각 요청은 1회였다.
같은 중간 종료 시험에서 B의 Goal을 삭제한 변형도 통과했다. 최신 B 이력은
유지되고 A의 과거 Goal은 되살아나지 않았다.

이 시험은 root-only stdio 연결을 직접 소유한다. 기존 사용자 TUI의 전체
보조 대화·초안·동시 입력을 차단하거나 실제 계정 인증을 이관했다는 증거는
아니다. 제품용 전체 소유권 관측, TUI 입력 장벽과 그룹/서버 이동 UI는 남아 있다.

## 선택 창의 터미널 입력 장벽 · 2026-11-11

네이티브 입력 장벽은 별도 private Unix socket과 환경변수로만 켜는 구현
후보다. 이벤트 루프가 장벽을 설치한 뒤 pause를 확인하며, 키·붙여넣기·
마우스 입력을 새 요청으로 전달하지 않는다. 기존 초안과 이미 접수한 작업은
유지한다. Esc, 제어 연결 종료, lease 만료는 장벽 해제를 요청한다.

lease 활성 여부와 실제 입력 장벽 설치 여부를 구분한다. 해제 후에도 장벽을
유지한 채 기존 Crossterm 입력 경계 처리로 decoded/raw typeahead와 미완성
붙여넣기를 비운다. 성공한 뒤에만 새 입력을 받고 release 성공을 반환한다.
입력 비우기가 실패하면 장벽을 유지하며 짧은 간격으로 재확인한다. 막았던
입력을 다른 계정에서 자동 재생하지 않는다.

Swift 제어 연결은 먼저 검증한 TUI의 커널 프로세스 신원과 같은 상대에게만
요청한다. 매 요청의 nonce, generation, lease, 상태와 실제 해제 확인을
검사하며 다른 응답이나 조기 해제 응답에는 연결을 닫는다. 이는 입력 장벽
확인이고 전체 대화 소유권·기존 작업 중단·이관 허가를 뜻하지 않는다.
입력 비우기 수정 후 네이티브 관련 검사 31개(입력 장벽 7개 포함)가 통과했다.
실제 두 TUI의 120×36/80×24 시험에서 차단 키·붙여넣기·단축키가 실행되지
않고, 다른 창은 편집 가능하며, 기존 초안과 명시적인 새 입력이 유지됐다.
해제 직전 typeahead와 미완성 붙여넣기도 재생되지 않았다. Swift 제어 연결의
pause/status/renew/release를 실제 TUI에 적용했고 기존 사용자 세션 4개는
유지됐다. 이 시험은 사용자 계정 인증이나 실제 그룹 이관을 실행하지 않는다.

세션 계정 패널에는 실제 연결 홈에 등록된 그룹 이름과 실제 소켓 상대의
app-server PID를 표시한다. 미등록 홈은 기존 Codex 홈으로 구분하며, PID는
숫자 구분자 없이 복사 가능하게 표시한다. 그룹 이름·메일이 긴 경우와
기존 홈·공유·개별·로딩·오류·잠김의 28개 네이티브 렌더를 생성해 대표
밝은/어두운 350pt/600pt 화면의 줄바꿈과 버튼 배치를 확인했다. 대상 그룹과
서버를 선택해 기존 대화를 이동하는 실행 UI는 아직 연결하지 않았다.
