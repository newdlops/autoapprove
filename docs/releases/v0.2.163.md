# 0.2.163 · 빌드 190

로컬 주소 상태를 확인할 때 큰 파일을 모두 적재한 뒤 거절하던 메모리 낭비를 줄였습니다. 내용 해석과 기존 주소 설정·Origin 규칙은 유지합니다.

- 열린 파일의 유형과 **1MiB** 크기 한도를 읽기 전에 확인합니다. 이미 큰 파일이면 내용은 **0바이트** 읽습니다.
- 읽는 도중 커져도 이번 조회 전체의 읽기·버퍼 예산은 최대 **1,048,577바이트**입니다. 크기·수정/변경 시각이 바뀌거나 길이가 맞지 않으면 해당 결과를 사용하지 않습니다.
- 정상 파일의 심볼릭 링크를 지원하며 파이프·디렉터리 때문에 기다리지 않습니다. 성공·실패 모두 파일 핸들을 닫습니다.
- 다음 조회는 파일을 새로 엽니다. 상태·권한·내용 캐시와 새 타이머·상주 서비스를 추가하지 않았습니다.

정식 0.2.162 읽기 본문의 고정 경로만 소유한 합성 파일 인자로 바꾸고 같은 실제 Core 파서를 사용했습니다. 후보는 실제 새 Core 읽기 함수를 측정합니다. **5조건·각 8쌍·새 80프로세스**에서 사전 CPU·wall·최대 RSS·읽기 예산 기준을 모두 통과했습니다. CPU는 8개 프로세스 중앙값, RSS는 8개 최대값입니다.

| 파일 크기 | CPU, 이전 → 수정 | 프로세스 최대 RSS, 이전 → 수정 | 새 읽기량 |
| --- | --- | --- | --- |
| 0바이트 | 0.437 → 0.427ms | 9.80 → 9.81MB | 0바이트 |
| 72바이트 | 0.465 → 0.427ms | 9.80 → 9.80MB | 72바이트 |

| 32MiB | 5.338 → 0.427ms | 43.34 → 9.73MB | 0바이트 |

32MiB 조건의 최대 RSS는 약 **77.5%**, CPU는 약 **92%** 줄었습니다. 정확히 1MiB 파일의 CPU는 약 **2.9% 증가**했으며 같은 텍스트 판정과 기존 한도를 유지합니다. 이는 격리된 합성 파일의 읽기 비교이며 설치 앱 전체 메모리·CPU나 휴대폰 지연 개선율이 아닙니다. 실제 시스템 hosts 파일은 이 비교에서 읽거나 수정하지 않았습니다.

관련 검사 **25개**, 최종 Release 전체 **426/426 · 270.198초**가 통과했습니다. 새 회귀 5개는 한글·결합문자·이모지·8종 줄바꿈·UTF-8 BOM/오류, 정확한 크기 경계, 파일 재작성·정상/끊긴 심볼릭 링크·FIFO·디렉터리·비파일 URL, 동시 증가 때의 실제 읽기 예산과 반복 성공/실패의 파일 핸들 해제를 확인합니다. 최초 한 건은 원문 문자열과 파일 디코딩의 BOM 처리 차이를 혼동해 4/5였으며, 기존/후보 파일 읽기가 모두 같은 결과임을 확인한 뒤 검사 기대값만 고쳤습니다. 제품 Core/App/CLI와 성능 실행 파일은 이 보완 전후가 같습니다.
