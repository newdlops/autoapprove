# AutoApprove 0.2.179 · build 206

같은 네트워크에서 다른 Mac을 찾는 기능과 웹 관리 페이지의 연결 복구를
개선했습니다. 이미 Mac 한 대를 찾은 뒤 남은 후보 검색을 늦추던 제한을
제거하고, 저장된 머신과 새 머신을 함께 확인합니다.

## 네트워크 검색과 복구

- 후보 주소를 한 번에 하나씩 확인하던 경로를 최대 8개 묶음으로 바꿨습니다.
  실제 검색 연결은 총 8개, 새 주소는 6개 이하로 제한해 저장된 머신의
  확인에도 여유를 남깁니다. 주소별 재검색 간격과 서브넷 범위는 유지합니다.
- 같은 LAN의 첫 Mac 발견 뒤에도 나머지 후보를 계속 확인합니다. Wi-Fi와
  Ethernet의 검색 순서를 공정하게 유지하고, Bonjour의 IP 변경도 기존
  경로·목록 검증 정보를 갱신합니다.
- 저장된 IP를 다른 머신이 받은 경우에도 새 머신을 별도 식별자로 찾습니다.
  반복 실패한 주소는 다시 식별하되, 원본 읽기·입력은 이전 식별자를 유지해
  다른 머신을 원본으로 오인하지 않습니다.
- 보조 전송 스크립트가 응답하지 않아도 웹 목록을 표시합니다. 네트워크·화면
  복귀는 멈춘 목록 요청을 교체하고, 일시 오류에는 빠른 재시도 후 간격을
  늘립니다. 정상 갱신 주기·조건부 응답·압축과 입력의 단일 전송은 유지합니다.
- 실제 Core를 연결한 합성 검사에서 응답 없는 주소 16개 뒤의 머신과 같은
  LAN의 두 번째 머신을 각각 약 4.1/4.1초에 찾았습니다. 변경 전에는 두 경우
  모두 같은 5.5초 예산 안에 찾지 못했습니다. 실물 네트워크 지연 수치는 아닙니다.
- 저장 IP의 새 소유자는 약 2.5초에 찾았고 이전 식별자는 오프라인으로 유지했습니다.
- 저장된 머신 발견/재시작 복구 580/572ms, 여러 인터페이스의 발견,
  오래된 저장 주소 32개, 단절·재발견과 기존 압축 검사를 통과했습니다.
  웹 복구는 Chromium/WebKit 각 5개 상황과 세 화면 크기로 검증했습니다.

## 기존 경량화 포함

터미널 비교·네트워크 주소 판별·gzip 버퍼·상태 응답과 승인 질문 처리에서
중복 변환과 임시 할당을 줄였습니다. 일반 선택 질문의 수동 응답,현재 모델
유지,위험 명령의 안전한 대안 유도와 원본 입력 검증은 유지합니다.

새 터미널 출력은 양쪽 Mac이 지원할 때 필드 존재 비트·자료형 태그·가변길이
정수·UUID/색상·PTY 바이트를 쓰는 바이너리 형식으로 협상합니다. 구버전은
기존 SSE를 사용하고,새 수신부도 SSE 응답으로 돌아갈 수 있습니다.
입력 API와 세션의 원본 식별은 바꾸지 않습니다.

고정 필드의 중복 확인에도 존재 비트를 재사용해 문자열 집합과 임시 슬롯의
비용을 줄였습니다. 출력 바이트 수는 같고,큰 정수의 정밀도는 유지합니다.

HTTP 제한 시간도 연결별 지연 작업 대신 리스너의 타이머 하나로 관리해,
연결 종료 뒤 잠시 남는 메모리를 줄였습니다. 기존30초·5초 제한은 유지합니다.

PTY 수신에서는 바이트→Base64→바이트 왕복을 제거했습니다. 느린 화면 처리
중에는 정확한 출력 바이트만 보관하며,완료된 위치부터 재개합니다.

## 검증과 측정 범위

- 공유 타이머의 실제 Core 비교에서512회 상태 조회 후 연결 재사용 경로의
  남은 힙이 약0.6MB 적었습니다.4경로의 연산량·메모리·대조 기준을 통과했습니다.
  고정 loopback 포트 재시작 오류49는 기존/후보와 앱 없는 별도 소켓에서도
  재현됐습니다. 실행 환경에 중간 계층이 관찰됐으며 제품 원인으로 확정하거나
  실물 네트워크의 재연결 문제가 해결됐다고 주장하지 않습니다.
- 비트마스크 인코더의 합성 비교에서 명령어 수는 평균 약13.6% 줄었습니다.
  실제 Core294연결의 추가 힙·해제·색상·커서·gzip 검사를 통과했습니다.
  전체 앱 CPU나 실물 네트워크 지연의 개선율은 아닙니다.
- 새 Core의 전체 451검사를 통과했습니다. 기존 경량화 검사는 별도의 합성
  경로 결과이며,개선율을 합산하거나 전체 앱 개선율로 해석하지 않습니다.
- 동일 객체 630개의 인코딩 바이트를 유지하면서 정상 출력 버퍼의 요청
  합계가 4,144,960→726,686바이트로 줄었습니다. 앱 전체 RAM/RSS 수치가 아닙니다.
- 인코딩/압축 18경로·180프로세스 비교의 명령어 기준을 통과했습니다.
- 실제 Core 연결 640회와 워밍업 16회의 연결 정리 후 추가 힙 증가 비교를
  통과했습니다. 기존 절대 힙 기준의 실패와 SSE/wire 공통 증가의 원인은
  남아 있으며,전체 앱 메모리가 최소라는 의미가 아닙니다.
- Chromium/WebKit의 원본 터미널 5경로는 수신 처리 시간이 25~51% 줄었고,
  대량 PTY 2경로의 바이트 준비는 94~98% 줄었습니다. 후자의 렌더 sink는
  동기 drain인 관찰기입니다. xterm painting·전체 앱 CPU·네트워크 지연이나
  물리 휴대폰의 개선율을 측정한 결과가 아닙니다.
- 최초 WebKit 대조 측정의 흔들림은 보존했습니다. 새 단일 realm/대칭
  워밍업 비교에서 A/B와 동일 코드 A/A의 사전 기준을 통과했습니다.
- 실제 Core gzip 스트리밍·복귀와 웹 Source/PTY/xterm의 ANSI/Unicode,
  느린 소비자의 완료 위치 재개,SSE/구버전 fallback을 확인했습니다.
  두 브라우저의 모바일·태블릿·데스크톱 캡처를 별도로 확인했습니다.

## 공개 재현

```sh
node scripts/terminal-wire-check.mjs --build=.build/release
node scripts/peer-stream-buffer-check.mjs --build=.build/release
node scripts/peer-stream-batch-check.mjs --build=.build/release
node scripts/peer-stream-batch-browser-check.mjs --build=.build/release
node scripts/stream-send-watchdog-check.mjs --build=.build/release
```

각 도구에는 일치하는 release 빌드를 지정해야 합니다. 객체 개수 고정 대신
SwiftPM의 출력 명세와 실제 객체 파일을 완전히 대조합니다. 브라우저가
필요한 검사는 별도 실행 환경을 요구합니다.
