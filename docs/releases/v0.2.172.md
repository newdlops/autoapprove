# 0.2.172 · 빌드 199

위험 명령을 검사할 때 NFC 정규화 뒤의 ASCII 공백 제거를 가볍게 처리합니다. 연속 UTF-8 입력을 끝까지 확인한 뒤 정확히 필요한 크기만 할당하며, 공백이 없거나 공백뿐인 경우에는 새 문자 배열을 만들지 않습니다. ASCII가 아닌 문자가 하나라도 있거나 연속 저장소를 사용할 수 없으면 기존 Character 판별을 사용합니다.

위험 후보 검색·Unicode case folding·승인 거절과 안내 정책·원본 검증은 유지합니다. 로컬 설치 파일에 의존하는 판정은 여전히 매번 새로 파일을 읽습니다. 위험 결과 캐시나 서비스, 타이머는 추가하지 않습니다.

정식171과 수정한 실제 Core에 같은 합성 입력을 연결해 **새32프로세스·엔진8쌍과 정책8쌍·1,152개 비교 구간**을 측정했습니다. 엔진은16세션·4저장 형식의 동일/변경 화면을 각128회 처리하며, 직접 위험 검사는10개 작업을 사용합니다. 각 프로세스 쌍 안에서 ABBA/BAAB 순서를 교대하고, 8개 구간의 비율 중앙값을 구한 뒤 독립8쌍의 중앙값을 최종 비율로 사용합니다. 아래 수치는 수정/이전 비율이며 절대 시간 중앙값을 나눈 값이 아닙니다.

ASCII 반복 갱신의 CPU는 **37.3~37.5%**, 변경 화면의 CPU는 **2.7~3.5%** 줄었습니다. 혼합문자의 CPU 증가는 최대 약0.6%였으며 사전 기준 안입니다. 직접 검사 CPU 비율은 짧은 일반 명령0.6127, 긴 일반 출력0.0955, 긴 출력 끝의 위험 명령0.9620, 읽기 전용 후보0.8924였습니다. 프로세스 최대RSS는 엔진 **30,556,160→30,195,712바이트**, 직접 검사 **17,956,864→17,842,176바이트**였습니다.

측정 전에 고정한 **CPU·경과 시간·메모리 38개 기준이 모두 통과**했습니다. 로그·종료 상태·1,152개 구간·판정/읽기/상태/발행 계수·394입력·양쪽94Core객체와16추가 연결객체를 별도 검토했습니다. 이 수치는 합성 Core 처리 범위의 결과이며 앱 전체·실물 휴대폰·네트워크·VPN·보안 검사 도구에서 같은 개선율을 측정한 것은 아닙니다.

본 비교 전에 같은 바이너리끼리의 대조에서 큰 변동을 확인했습니다. 파일 검증을 경계로 옮기고 짧은 비교 구간을 교대하며 로그 쓰기를 묶는 측정 방식을 후보 시간 측정 전에 고정했습니다. 마지막 동일 바이너리 대조도 두 쌍뿐이고 최대 경과 시간 편차가18.8%여서 변동이 사라졌다고 보지 않습니다. 외부 검사 도구나 스케줄러를 원인으로 단정하지 않았으며, 본 비교에서 표본을 제외·재시도하거나 38개 수치 기준을 완화하지 않았습니다.

검증:

- 정식171 소스와 ASCII triple **2,097,152개**, 유효 Unicode scalar **1,112,064개**, 정확한 UTF-8 공백 제거 **5,480,262회**, 정책6,642건·도구 요청2,040건을 대조했습니다. foreign1,359건·파일 변경에 따른 판정 변화56건과 두 거절 이벤트의 정확한 JSON도 같습니다. digest는 `f2f98b6bfc54d1c650ab753b7176e20ce16a4de4e2f8f939dfefd709a8faf9ae`입니다.
- 관련35검사와 공개 정합성 재현 도구가 통과했습니다. 공개 벤치마크의 별도1쌍·4프로세스·144구간 기능 검사도 통과했으며 채택 근거인8쌍 표본과 섞지 않았습니다.
- 최종 버전 자원의 빌드는399입력과94Core객체를 확인했고, 성능 비교에 쓴 수정 Core의 객체 바이트가 모두 유지됐습니다. 이전/수정 모듈 SHA는 같지만3객체가 다르므로 모듈 해시만으로 코드 동일성을 판단하지 않습니다.
- 최종 Release 전체 **450/450 checks passed · 223.066초**가 통과했습니다. 기존 발행자 서명의 패키지 통합3종·DMG 검증도 통과했으며, App/CLI코드와 runtime·웹13파일이 검사한 빌드와 일치했습니다. 키체인 검색 목록·인증서·신뢰·ACL은 변경하지 않았습니다.

169부터 앱이 덮개 상태를 근거로 직접 강제 잠자기를 요청하던 경로를 제거한 수정도 포함합니다. 작업 중 기존 잠자기 방지는 유지하지만 일반 앱의 유휴 방지 API는 덮개 닫힘에 의한 강제 잠자기·내장 화면 꺼짐을 보장해서 차단하지 않습니다([Apple 공식 설명](https://developer.apple.com/library/archive/qa/qa1340/_index.html)). 이 버전을 macOS 덮개 오감지의 해결로 보아서는 안 됩니다. 설치 앱 교체·재시작, 원본 터미널 조작·잠금 해제·실제 전원 명령·자동 실행/별도 서비스 등록·관리자 상승·시스템/보안/TCC/VPN 정책 변경은 하지 않았습니다. 새 브라우저·실물 휴대폰 시각 검증도 없습니다.
